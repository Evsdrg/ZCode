# 自部署 WebUI 连接韧性（WS 保活 + 断线重连）

状态：实施中
适用范围：`zcode --web` 自部署形态的浏览器主连接（`/ws`，web-remote-replayable）。

## 背景

自部署链路上最容易掉的长连接是**浏览器 ↔ edge-proxy ↔ 隧道 ↔ 本机 Host 的 `/ws`**：

- 它既没有应用层心跳，也没有断线重连（web 客户端 `onClose: () => {}` 是空处理）；
- 一旦空闲（模型静默思考、长工具执行）或中间有状态的网络设备（阿里云 NAT/网关、mesh
  抖动）设了空闲超时，连接被掐断后 UI 静默卡死，只能手动刷新；
- 仓库里虽有 `PersistentProtocol`（5s KeepAlive + 20s ACK 超时 + 重放），但它只接在桌面
  远端连接路径（`rpc/remote.ts`），浏览器 `/ws` 用的是裸 `SocketProtocol`。

需要先明确一个边界：**跨重连的透明会话续传（`replaceSocket` + ACK 重放）在这里不可用**——
服务端每次 upgrade 都新建 `ChannelServer`（会话无连续），对端不 ACK 时 `PersistentProtocol`
还会在 20s 后主动断链。因此本方案不做协议级会话续传，只做两件事：**保活**与**可恢复重连**。

## 行为规则

| 能力           | 做法                                                                               | 判定依据                                                                               |
| -------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 服务端心跳保活 | Host 对每个 `/ws` 连接周期性发送 WS Ping 控制帧；`ws` 自动回 Pong                  | WS Ping 是真实帧，双向产生流量，重置各跳空闲计时器；浏览器按规范自动回 Pong（无需 JS） |
| 半死连接检测   | 超过 2 个心跳周期未收到 Pong → `terminate()`                                       | 半开连接（对端进程已死/网络黑洞）无法靠 TCP 感知，靠 Pong 缺失判定                     |
| 浏览器断线重连 | 主连接非预期关闭后进入重连态：持续探测可达性（`/api/server-info`），可达即整页重载 | RPC 层无法跨连接续传，整页重载是最可靠的再引导（复用既有 bootstrap 流程）              |
| 可见提示       | 重连期间显示覆盖层「连接已断开，正在重连…」                                        | 用户必须能区分"卡住"与"在重连"                                                         |

## 状态所有者

- **心跳的所有者**：Host `setupChannelServer`（单连接生命周期内），随连接关闭清理定时器。
- **重连态的所有者**：web 入口 `main.tsx` 的启动编排（单一 `reconnecting` 标志 + 覆盖层），
  不引入全局 store；重连成功即以既有的 bootstrap 路径重建整个应用。

## 事件顺序

```
浏览器打开 → connectViaWebSocket 成功（open）→ 正常使用
  ├─ 服务端每 25s 发 Ping；浏览器自动回 Pong
  ├─ 2×25s 无 Pong → 服务端 terminate → 浏览器收到 close
  └─ 网络设备掐断 → 浏览器收到 close

浏览器 close（非预期，且此前已 open）
  → 渲染「正在重连…」覆盖层，置 reconnecting=true（幂等，忽略重复 close）
  → 循环：退避等待 → fetch /api/server-info 探测
      可达（含 401）→ window.location.reload()（重新 bootstrap，覆盖层随新页面消失）
      不可达 → 继续退避重试（覆盖层保留，用户可见）

页面卸载（beforeunload）→ 置 shuttingDown，close 不再触发重连
```

幂等边界：重复 close 只重连一次；重连态下不再叠加覆盖层；卸载中的 close 不重连。

## 失败语义

- 探测 HTTP 状态为任意响应（含 401 鉴权失败）都视为"服务可达"→ 重载；重载后若鉴权失效，
  由既有 bootstrap 错误页兜底（含手动重试）。
- 服务长时间不可达：覆盖层保留并持续退避重试，不无限快速重连。
- 服务端 Ping 抛错（连接已关闭竞态）：忽略，不推进程。

## 不变量

1. **不改协议与会话语义**：不引入 `PersistentProtocol` 到浏览器 `/ws`（避免 ACK/重放与服务端
   每连接新建会话的冲突）；心跳只用 WS 控制帧，业务负载格式不变。
2. **不改 `/ws` 的首帧与鉴权**：心跳帧与 RPC 帧分离，edge-proxy 的 token/Basic 校验、Host 的
   token 校验均不感知心跳。
3. **心跳不得拖垮进程**：定时器随连接关闭清理；Ping 调用包裹异常，任何失败只终止当前连接。

## 验收场景

1. 空闲连接（≥5 分钟无业务流量）不再被中间设备掐断：页面保持在线。
2. 手动 kill 本机 Host 或断开隧道：浏览器出现「正在重连…」覆盖层；恢复后自动回到可用界面。
3. 服务不可达期间覆盖层保留、退避重试，不白屏、不静默卡死。
4. 页面正常关闭/跳转不触发重连。
5. 桌面形态不受影响（桌面走 stdio/messageport，不经 `/ws` 心跳路径）。

## 测试

- 服务端心跳：单测覆盖"定时发 Ping / 无 Pong 超时 terminate / close 清理定时器"（注入 fake ws）。
- 浏览器重连编排：纯逻辑单测覆盖状态机（重复 close 幂等、卸载不重连、退避序列、可达判定）。
